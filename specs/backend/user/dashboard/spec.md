# Feature Specification: 사용자 대시보드

**Feature Branch**: `feature/user-dashboard-backend-docs`
**Status**: Draft

## User Scenarios & Testing

### User Story 1 - 내 정보 관리 조회 (Priority: P1)

> 사용자는 마이페이지에서 자신의 계정 정보와 GitHub 연동 상태를 확인하여 계정 상태를 관리할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 마이페이지에 접속한 상태에서, **When** 내 정보 조회 API를 요청하면, **Then** 이름, 이메일, 휴대폰 번호, 회원 유형, 계정 상태, 가입일 정보를 반환한다.

2. **Given** 로그인한 사용자가 GitHub URL을 등록한 상태에서, **When** GitHub 연동 정보 조회 API를 요청하면, **Then** GitHub URL과 연동 여부를 반환한다.

3. **Given** 로그인한 사용자가 GitHub URL을 등록하지 않은 상태에서, **When** GitHub 연동 정보 조회 API를 요청하면, **Then** 연동되지 않은 상태 정보를 반환한다.

---

### User Story 2 - 스크랩 공고 조회 (Priority: P1)

> 사용자는 저장한 채용공고 목록을 조회하여 관심 공고를 관리할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 채용공고를 스크랩한 상태에서, **When** 스크랩 공고 목록 조회 API를 요청하면, **Then** 사용자의 스크랩 공고 목록을 반환한다.

2. **Given** 사용자가 검색어를 입력한 상태에서, **When** 스크랩 공고 목록 조회 API를 요청하면, **Then** 검색 조건에 일치하는 공고만 반환한다.

3. **Given** 사용자가 스크랩한 공고 중 기업에 의해 삭제된 공고가 존재하는 상태에서, **When** 스크랩 공고 목록을 조회하면, **Then** 삭제 상태가 표시된 공고 정보를 반환한다.

---

### User Story 3 - 스크랩 공고 해제 (Priority: P2)

> 사용자는 더 이상 관심 없는 채용공고의 스크랩을 해제하여 목록을 관리할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 스크랩한 공고가 존재하는 상태에서, **When** 스크랩 해제 API를 요청하면, **Then** 해당 스크랩 정보가 제거된다.

2. **Given** 사용자가 본인의 스크랩 공고를 해제한 상태에서, **When** 목록을 다시 조회하면, **Then** 해제된 공고가 목록에서 제거된다.

---
### User Story 4 - 회원 정보 수정 (Priority: P2)

> 사용자는 마이페이지에서 이름, 휴대폰 번호, GitHub URL을 수정하여 프로필 정보를 최신 상태로 유지할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 회원 정보 수정 모달을 연 상태에서, **When** 이름, 휴대폰 번호, GitHub URL을 입력하고 저장하면, **Then** 수정된 회원 정보가 저장된다.

2. **Given** 사용자가 잘못된 형식의 휴대폰 번호 또는 GitHub URL을 입력한 상태에서, **When** 저장을 요청하면, **Then** 입력값 검증 오류를 반환한다.


### Edge Cases

* 사용자가 존재하지 않는 스크랩 공고를 해제하면 어떻게 처리되는가?
* 삭제된 채용공고가 스크랩 목록에 존재하면 어떤 정보를 반환하는가?
* GitHub URL이 등록되지 않은 사용자는 어떤 응답을 받는가?
* 사용자가 다른 회원의 스크랩 공고에 접근을 시도하면 어떻게 처리되는가?
* 스크랩 공고가 하나도 없는 경우 어떤 응답을 반환하는가?

## Requirements

### Functional Requirements

* **FR-001**: 시스템은 로그인한 사용자의 기본 정보를 조회할 수 있어야 한다.
* **FR-002**: 시스템은 로그인한 사용자의 GitHub 연동 정보를 조회할 수 있어야 한다.
* **FR-003**: 시스템은 로그인한 사용자의 스크랩 공고 목록을 조회할 수 있어야 한다.
* **FR-004**: 시스템은 검색 조건에 따라 스크랩 공고를 필터링할 수 있어야 한다.
* **FR-005**: 시스템은 최신순 기준으로 스크랩 공고를 정렬할 수 있어야 한다.
* **FR-006**: 시스템은 삭제된 채용공고를 삭제 상태와 함께 반환할 수 있어야 한다.
* **FR-007**: 시스템은 사용자가 스크랩한 공고를 해제할 수 있어야 한다.
* **FR-008**: 시스템은 본인 소유 데이터만 조회 및 관리할 수 있어야 한다.
* **FR-009**: 모든 API는 ApiResponse 형식으로 응답해야 한다.
* **FR-010**: 모든 예외는 ErrorCode와 CustomException 기반으로 처리해야 한다.
* **FR-011**: 시스템은 로그인한 사용자의 이름, 휴대폰 번호, GitHub URL을 수정할 수 있어야 한다.
* **FR-012**: 시스템은 회원 정보 수정 요청값의 형식을 검증할 수 있어야 한다.

### Key Entities

* **Member**: 회원 식별자, 로그인 ID, 이메일, 이름, 회원 유형, 계정 상태, 구독 상태, 가입일
* **PersonalProfile**: 휴대폰 번호, GitHub URL
* **Bookmark**: 회원별 스크랩 채용공고 정보
* **JobNotice**: 채용공고 정보 및 공고 상태

## Success Criteria

* **SC-001**: 로그인 사용자는 자신의 계정 정보를 정상 조회할 수 있다.
* **SC-002**: 로그인 사용자는 GitHub 연동 상태를 확인할 수 있다.
* **SC-003**: 로그인 사용자는 스크랩 공고 목록을 조회할 수 있다.
* **SC-004**: 삭제된 채용공고가 포함된 경우에도 목록 조회가 가능하다.
* **SC-005**: 스크랩 해제 요청 시 대상 공고가 목록에서 제거된다.
* **SC-006**: 타인 데이터 접근 시 권한 오류가 반환된다.
* **SC-007**: 회원 정보 수정 요청 시 변경된 값이 다음 조회 응답에 반영된다.

## Assumptions

* 사용자 API는 최신 Convention 기준인 `/api/v1/user/{domain}` 경로를 사용한다.
* Dashboard 도메인은 `members`, `personal_profiles`, `bookmarks`, `job_notices` 테이블을 사용한다.
* GitHub OAuth 실제 연동 기능은 v2 범위에서 구현한다.
* GitHub ID 조회 및 GitHub OAuth 기반 계정 연동 기능은 v1 범위에 포함하지 않는다.
* 삭제된 채용공고는 스크랩 목록에 유지하며 삭제 상태로 표시한다.
* 채용공고 상세 조회 기능은 JobNotice 도메인에서 제공한다.
* 모든 API는 JWT 인증 및 `ROLE_USER` 권한을 필요로 한다.
* 삭제된 채용공고의 상세 조회 정책은 JobNotice 도메인 정책을 따른다.
* 회원 정보 수정 범위는 이름, 휴대폰 번호, GitHub URL로 제한한다.
* `githubId`는 GitHub OAuth 연동(v2) 도입 전까지 `null`을 반환할 수 있다.
