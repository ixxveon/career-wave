# Feature Specification: JobNotice User Backend

**Feature Branch**: `feature/job-notice-backend-spec`
**Status**: Draft

## User Scenarios & Testing

### User Story 1 - 채용 공고 목록 및 상세 조회 (Priority: P1)

> 사용자는 공개 중인 채용 공고를 목록과 상세 화면에서 조회할 수 있다.

**Acceptance Scenarios**:

1. **Given** 공개 상태의 채용 공고가 존재하는 상태에서, **When** 사용자가 채용 공고 목록 조회를 요청하면, **Then** 시스템은 공개 가능한 공고만 페이지네이션 형태로 반환해야 한다.
2. **Given** 특정 채용 공고가 공개 상태로 존재하는 상태에서, **When** 사용자가 상세 조회를 요청하면, **Then** 시스템은 공고 본문과 노출 필드를 반환해야 한다.
3. **Given** 비로그인 사용자가 목록 또는 상세 조회를 요청한 상태에서, **When** 대상 공고가 공개 상태이면, **Then** 시스템은 인증 없이도 동일한 조회 결과를 반환해야 한다.
4. **Given** 존재하지 않거나 공개 종료된 채용 공고를 조회하는 상태에서, **When** 사용자가 상세 조회를 요청하면, **Then** 시스템은 정의된 오류 응답을 반환해야 한다.

---

### User Story 2 - 채용 공고 북마크 등록 및 해제 (Priority: P1)

> 로그인한 사용자는 관심 있는 채용 공고를 북마크로 저장하거나 해제할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 아직 북마크하지 않은 공개 공고를 보고 있는 상태에서, **When** 북마크 등록을 요청하면, **Then** 시스템은 해당 사용자와 공고의 북마크 관계를 생성해야 한다.
2. **Given** 로그인한 사용자가 이미 북마크한 공고를 보고 있는 상태에서, **When** 북마크 해제를 요청하면, **Then** 시스템은 기존 북마크 관계를 제거해야 한다.
3. **Given** 비로그인 사용자가 북마크 등록 또는 해제를 시도하는 상태에서, **When** 요청을 보내면, **Then** 시스템은 인증 필요 오류를 반환해야 한다.
4. **Given** 동일 사용자가 동일 공고에 대해 중복 등록을 요청하는 상태에서, **When** 중복 북마크가 발생하면, **Then** 시스템은 중복 생성 없이 정의된 오류 응답을 반환해야 한다.

---

### User Story 3 - 조건 기반 공고 탐색 (Priority: P2)

> 사용자는 검색어와 필터, 정렬, 페이지네이션을 이용해 원하는 공고를 탐색할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 검색어와 필터 조건을 입력한 상태에서, **When** 목록 조회를 요청하면, **Then** 시스템은 확정된 Query Parameter 규격에 맞는 결과만 반환해야 한다.
2. **Given** 사용자가 `page`, `size`를 포함한 목록 조회를 요청한 상태에서, **When** 페이지네이션이 적용되면, **Then** 시스템은 외부 계약 기준 1-based 페이지 정보를 반환해야 한다.
3. **Given** 사용자가 허용되지 않은 필터 값 또는 잘못된 페이지 값을 전달한 상태에서, **When** 목록 조회를 요청하면, **Then** 시스템은 정의된 검증 오류를 반환해야 한다.

---

### Edge Cases

* 존재하지 않는 `jobNoticeId`로 상세 조회, 북마크 등록, 북마크 해제를 요청하면 어떻게 처리하는가?
* `notice_status = CLOSED` 공고는 목록과 상세에서 모두 비노출 처리되는가?
* 비로그인 요청에서 `bookmarked` 값은 항상 `false`로 고정되는가?
* 로그인 요청에서 북마크 여부는 현재 사용자 기준으로만 계산되는가?
* 동일 사용자의 동일 공고 북마크 중복 생성은 차단되는가?
* 북마크 해제 시 북마크 관계가 없으면 정의된 오류를 반환하는가?
* `page`, `size`가 1-based 외부 계약을 따르되 내부 Pageable 변환 시 `page - 1`이 적용되는가?

## Requirements

### Functional Requirements

* **FR-001**: 시스템은 비로그인 사용자에게도 공개 상태 채용 공고 목록 조회 기능을 제공해야 한다.
* **FR-002**: 시스템은 비로그인 사용자에게도 공개 상태 채용 공고 상세 조회 기능을 제공해야 한다.
* **FR-003**: 시스템은 채용 공고 목록 조회 시 확정된 Query Parameter(`keyword`, `jobType`, `jobCategory`, `careerLevel`, `location`, `companySize`, `period`, `sort`, `page`, `size`)를 지원해야 한다.
* **FR-004**: 시스템은 목록 조회 응답을 `ApiResponse<T>` 래퍼와 페이지네이션 구조(`content`, `page`, `size`, `totalElements`, `totalPages`)로 반환해야 한다.
* **FR-005**: 시스템은 상세 조회 응답에 공고 식별 정보, 회사 정보, 공고 설명, 분류 정보, 원문 URL, 마감일, 북마크 여부를 포함해야 한다.
* **FR-006**: 시스템은 `notice_status = ACTIVE`인 채용 공고만 사용자 조회 대상에 포함해야 한다.
* **FR-007**: 시스템은 로그인 사용자에게 채용 공고 북마크 등록 기능을 제공해야 한다.
* **FR-008**: 시스템은 로그인 사용자에게 채용 공고 북마크 해제 기능을 제공해야 한다.
* **FR-009**: 시스템은 북마크 API를 `POST /api/v1/user/job-notices/{jobNoticeId}/bookmarks`, `DELETE /api/v1/user/job-notices/{jobNoticeId}/bookmarks` 경로로 제공해야 한다.
* **FR-010**: 시스템은 북마크 등록 및 해제를 `USER` 권한 사용자에게만 허용해야 하며, Spring Security에서는 `ROLE_USER`로 매핑해야 한다.
* **FR-011**: 시스템은 동일 사용자와 동일 공고의 북마크 관계를 1건만 허용해야 한다.
* **FR-012**: 시스템은 Optional 인증 API에서 비로그인/로그인 응답 차이를 `bookmarked` 필드로 구분해야 한다.
* **FR-013**: 시스템은 존재하지 않거나 비공개 상태의 공고 요청에 대해 정의된 `ErrorCode` 기반 오류 응답을 반환해야 한다.
* **FR-014**: 시스템은 잘못된 필터 값, 잘못된 페이지 요청에 대해 정의된 검증 오류 응답을 반환해야 한다.
* **FR-015**: 시스템은 사용자 API 구현과 문서화를 `user` 패키지 범위 안에서 유지해야 하며 관리자 기능 요구사항을 포함하지 않아야 한다.
* **FR-016**: 시스템은 Service 계층을 인터페이스와 구현체(`impl`)로 분리해야 한다.
* **FR-017**: 시스템은 공통 오류 코드를 `global.exception.ErrorCode`에서 관리하고, JobNotice 도메인 전용 오류 코드는 도메인 `exception` 패키지에서 분리 관리해야 한다.

### Key Entities

* **JobNotice**: 채용 공고 본문, 회사명, 제목, 설명, 기술 태그, 채용 유형, 직무 분류, 경력 수준, 지역, 회사 규모, 급여, 원문 URL, 조회 수, 마감일, 공고 상태를 관리하는 엔티티
* **Bookmark**: 사용자와 채용 공고 사이의 북마크 관계를 관리하는 엔티티

## Success Criteria

* **SC-001**: 공개 상태 공고만 목록 및 상세 조회 응답에 포함된다.
* **SC-002**: 비로그인 사용자는 목록/상세 조회를 100% 수행할 수 있고, 북마크 API는 100% 인증 오류로 차단된다.
* **SC-003**: 로그인 사용자의 북마크 등록/해제 요청은 각각 정확히 1건의 관계 생성 또는 삭제만 반영한다.
* **SC-004**: 중복 북마크 등록 요청은 중복 데이터 없이 정의된 오류 응답으로 처리된다.
* **SC-005**: 모든 사용자 JobNotice API 응답은 `ApiResponse<T>` 규격과 확정된 DTO 계약을 만족한다.
* **SC-006**: 목록 조회 API는 1-based 페이지 응답 구조를 유지하고, 필터/정렬/페이지 조건이 결과에 반영된다.

## Assumptions

* 본 문서는 `jobNotice` 사용자 백엔드 기능 범위만 다루며 관리자 대시보드, 관리자 계정, ACL, AI 메트릭스, 감사 로그, 스크래핑 기능은 범위 외로 본다.
* 사용자 JobNotice 조회 및 북마크 기능은 Spring Boot 백엔드에서 직접 처리하며 FastAPI 연동은 없다.
* Query Parameter, API 경로, ERD 컬럼 및 Enum 값은 이미 확정되었으며 본 문서는 해당 계약을 기준으로 기능 요구사항만 정리한다.
