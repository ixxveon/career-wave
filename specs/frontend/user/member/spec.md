## 1. User Scenarios & Testing

### User Story 1 — 개인/기업 로그인 (Priority: P1)
> 사용자는 본인의 회원 유형에 맞게 로그인하고, 계정 상태에 따라 적절한 다음 화면 또는 제한 안내를 확인하고 싶다.

**Acceptance Scenarios**:
1. **Given** 사용자가 `/auth/login`에 진입하면, **When** 개인/기업 탭을 전환할 때, **Then** 동일 라우트에서 로그인 폼의 회원 유형 상태만 변경된다.
2. **Given** 유효한 아이디/비밀번호를 입력하면, **When** 로그인 버튼을 클릭할 때, **Then** 로그인 요청이 1회만 전송되고 성공 시 권한/상태 기반 라우팅이 수행된다.
3. **Given** 승인 대기 기업회원이 로그인하면, **Then** 일반 서비스 진입 대신 승인 대기 안내와 고객센터/홈 CTA가 표시된다.
4. **Given** 정지, 잠금, 블랙리스트 계정이 로그인 시도하면, **Then** 상세 내부 사유 없이 제한 안내와 복구 가능한 CTA만 표시된다.

### User Story 2 — 개인회원 가입 (Priority: P1)
> 개인 사용자는 아이디 중복 확인, 이메일/휴대폰 인증, 약관 동의를 완료하여 안전하게 회원가입하고 싶다.

**Acceptance Scenarios**:
1. **Given** 사용자가 개인회원 탭을 선택하면, **When** 필수 입력과 필수 약관 동의를 완료하기 전까지, **Then** 가입하기 버튼은 비활성화된다.
2. **Given** 사용자가 아이디 중복 확인을 완료하지 않았으면, **When** 가입하기를 시도할 때, **Then** 중복 확인 필요 메시지가 표시된다.
3. **Given** 인증번호가 만료되면, **When** 사용자가 확인 버튼을 클릭할 때, **Then** 만료 안내와 재전송 CTA가 표시된다.
4. **Given** 비밀번호와 비밀번호 확인이 다르면, **Then** 제출 전 오류 메시지가 표시되고 API 요청은 발생하지 않는다.

### User Story 3 — 기업회원 가입 및 승인 대기 (Priority: P1)
> 기업 담당자는 기업정보, 담당자 정보, 재직증명서 PDF를 제출하고 승인 대기 상태를 확인하고 싶다.

**Acceptance Scenarios**:
1. **Given** 사용자가 기업회원 탭을 선택하면, **Then** 기업정보, 담당자 정보, 재직증명서 업로드 영역이 표시된다.
2. **Given** PDF가 아닌 파일이나 허용 용량을 초과한 파일을 업로드하면, **Then** 업로드가 차단되고 오류 안내가 표시된다.
3. **Given** 필수 기업정보, 담당자 인증, PDF 첨부가 완료되면, **When** 가입 신청을 제출할 때, **Then** 가입 신청 완료 모달과 승인 대기 안내가 표시된다.
4. **Given** 이미 등록된 사업자등록번호로 가입 신청하면, **Then** 중복 기업 안내가 표시되되 기존 담당자 개인정보는 노출하지 않는다.

### User Story 4 — 소셜 가입 추가정보 입력 (Priority: P2)
> 소셜 계정으로 시작한 사용자는 부족한 필수 정보를 입력하고 서비스 가입을 완료하고 싶다.

**Acceptance Scenarios**:
1. **Given** 소셜 인증 이후 `/auth/register/verify`에 진입하면, **Then** 소셜 provider 기반 기본 정보와 추가 입력 폼이 표시된다.
2. **Given** 이름, 휴대폰 인증, 필수 약관 동의가 완료되면, **When** 가입 완료를 클릭할 때, **Then** 추가정보 저장 요청 후 가입 완료 화면으로 이동한다.
3. **Given** 소셜 provider 이메일이 이미 일반 계정과 연결되어 있으면, **Then** 계정 연결 또는 로그인 안내를 표시한다.

### User Story 5 — 아이디 찾기 (Priority: P1)
> 사용자는 개인/기업회원 유형에 맞는 인증을 거쳐 본인의 로그인 아이디 일부를 확인하고 싶다.

**Acceptance Scenarios**:
1. **Given** 사용자가 `/auth/find-account`에서 개인회원 아이디 찾기를 선택하면, **Then** `/auth/find-id/user`로 이동한다.
2. **Given** 개인회원이 이메일 또는 휴대폰 인증을 완료하면, **Then** 마스킹된 아이디 목록과 로그인 CTA가 표시된다.
3. **Given** 기업회원이 담당자명, 사업자등록번호, 담당자 이메일 인증을 완료하면, **Then** 마스킹된 기업회원 아이디가 표시된다.
4. **Given** 일치하는 계정이 없어도, **Then** 가입 여부를 직접 노출하지 않는 일반 안내 문구를 사용한다.

### User Story 6 — 비밀번호 재설정 (Priority: P1)
> 사용자는 본인 인증 후 새 비밀번호를 설정하여 계정 접근을 복구하고 싶다.

**Acceptance Scenarios**:
1. **Given** 사용자가 아이디와 인증 수단을 입력하면, **When** 인증이 완료될 때, **Then** 서버가 발급한 재설정 권한을 기준으로 새 비밀번호 입력 영역이 활성화된다.
2. **Given** 새 비밀번호가 정책을 만족하지 않으면, **Then** 저장 버튼은 비활성화되고 정책 안내가 표시된다.
3. **Given** 재설정 토큰이 만료되면, **When** 저장을 시도할 때, **Then** 인증 재시작 안내가 표시된다.

## 2. Requirements

### Functional Requirements

- **FR-001**: `/auth/login`은 개인/기업 탭 전환, 아이디/비밀번호 입력, 소셜 로그인 버튼, 아이디 찾기/비밀번호 찾기/회원가입 링크를 제공한다.
- **FR-002**: 로그인 요청은 중복 제출을 방지하고, 성공 후 `memberType`, `memberStatus`, `companyApprovalStatus`에 따라 라우팅 또는 제한 안내를 수행한다.
- **FR-003**: 로그인 실패 메시지는 계정 존재 여부를 노출하지 않는 일반 문구를 기본으로 한다.
- **FR-004**: `/auth/register`는 개인회원/기업회원 탭을 동일 페이지에서 전환한다.
- **FR-005**: 개인회원 가입은 아이디 중복 확인, 이메일/휴대폰 인증, 비밀번호 검증, 필수 약관 동의를 요구한다.
- **FR-006**: 기업회원 가입은 기업정보, 담당자 정보, 담당자 인증, 재직증명서 PDF 업로드를 요구한다.
- **FR-007**: 재직증명서 파일은 PDF, 허용 용량, MIME 타입을 프론트에서 1차 검증하고 서버 검증 실패도 UI에 반영한다.
- **FR-008**: `/auth/register/verify`는 소셜 가입 추가정보 입력, 휴대폰 인증, 약관 동의를 제공한다.
- **FR-009**: `/auth/find-account`는 개인/기업회원 선택 카드와 아이디/비밀번호 찾기 진입 CTA를 제공한다.
- **FR-010**: `/auth/find-id/:memberType`은 회원 유형별 인증 필드를 제공하고, 결과는 마스킹된 아이디로 표시한다.
- **FR-011**: `/auth/find-password/:memberType`은 본인 인증 완료 후에만 새 비밀번호 입력을 활성화한다.
- **FR-012**: 인증번호 발송/확인/재전송은 로딩, 성공, 실패, 만료, 쿨다운, 요청 횟수 제한 상태를 표시한다.
- **FR-013**: 승인 대기/반려/보완 필요 기업회원 상태는 서비스 진입 제한과 재신청/문의 CTA를 제공한다.
- **FR-014**: 401 토큰 만료는 access token 갱신 또는 세션 복원 시도를 1회 수행한 뒤, 실패 시 세션 정리 후 로그인 페이지로 이동하며, 작성 중 폼 데이터는 민감정보를 제외하고 필요 시 복원 가능해야 한다.
- **FR-015**: 429 rate limit 응답은 재시도 가능 시간 또는 일반 제한 안내를 표시한다.

### Non-functional Requirements

- **NFR-001**: 로그인/가입/복구 화면은 모바일 375px 기준에서 입력 필드와 버튼 텍스트가 겹치지 않아야 한다.
- **NFR-002**: 인증번호 입력, 약관 체크, 탭 전환, 모달은 키보드로 조작 가능해야 한다.
- **NFR-003**: 비밀번호, 인증번호, token은 `localStorage` 같은 지속성 브라우저 저장소에 저장하지 않는다. 단, 새로고침 이후 로그인 상태가 즉시 해제되지 않도록 memory + refresh cookie 기반 세션 복원 경로 또는 이에 준하는 보안 대안을 제공해야 한다.
- **NFR-004**: 사용자 입력값은 HTML로 직접 렌더링하지 않는다.
- **NFR-005**: 네트워크 실패 시 사용자가 같은 작업을 안전하게 재시도할 수 있어야 한다.
- **NFR-006**: Lighthouse 접근성 95점 이상을 목표로 한다.

### Key Entities

- **Member**: `memberId`, `loginId`, `name`, `email`, `phone`, `memberType`, `memberStatus`, `lastLoginAt`, `createdAt`
- **CompanyProfile**: `companyProfileId`, `memberId`, `companyName`, `businessNumber`, `ceoName`, `address`, `addressDetail`, `companyType`, `isAgency`, `approvalStatus`
- **VerificationSession**: `verificationId`, `channel`, `target`, `status`, `expiresAt`, `resendAvailableAt`, `remainingAttempts`
- **PasswordResetSession**: `resetToken`, `loginId`, `memberType`, `expiresAt`
- **SanctionSummary**: `memberStatus`, `restrictionType`, `recoverable`, `availableAt`

## 3. Edge Cases 및 해결 정책

- **계정 존재 여부 추론 위험**: 로그인/찾기/재설정 실패 메시지는 기본적으로 일반화한다.
- **인증번호 만료**: 입력 영역은 유지하되 확인 버튼은 실패 처리하고 재전송 CTA를 강조한다.
- **인증번호 재전송 과다**: 429 응답 시 남은 시간 또는 고객센터 안내를 표시한다.
- **중복 클릭**: 로그인, 가입, 인증 확인, 비밀번호 저장 버튼은 요청 중 disabled 처리한다.
- **사업자등록번호 중복**: 이미 등록된 기업임을 안내하되 기존 담당자명/이메일은 노출하지 않는다.
- **PDF 위장 파일**: 프론트 MIME 검증 실패 시 차단하고, 서버 악성 파일 검사 실패 응답도 오류로 표시한다.
- **기업 승인 대기 중 로그인**: 로그인 자체는 성공할 수 있으나 protected service route 대신 승인 대기 화면으로 이동한다.
- **정지/영구정지/블랙리스트**: 서비스 접근 차단. 상세 내부 정책, 신고자 정보, 탐지 기준은 노출하지 않는다.
- **토큰 만료**: FR-014 기준으로 access token 갱신 또는 세션 복원을 1회 시도하고, 실패 시 세션을 정리한 뒤 로그인 페이지로 이동한다. 이때 작성 중이던 폼 데이터는 비민감 정보에 한해 복원 가능해야 한다.
- **소셜 계정 충돌**: 기존 이메일과 충돌 시 계정 연결 또는 기존 로그인 안내를 표시한다.

## 4. Success Criteria

- **SC-001**: 개인/기업 로그인 탭 전환, 로그인 요청, 상태별 제한 안내가 정상 동작한다.
- **SC-002**: 개인회원 가입은 중복 확인, 인증, 약관, 비밀번호 조건을 모두 만족해야 제출 가능하다.
- **SC-003**: 기업회원 가입은 PDF 첨부 및 담당자 인증 없이는 제출되지 않는다.
- **SC-004**: 아이디 찾기/비밀번호 찾기는 계정 존재 여부를 직접 노출하지 않는다.
- **SC-005**: 인증번호 만료, rate limit, 네트워크 실패, 토큰 만료 상태가 UI에서 복구 가능하게 처리된다.
- **SC-006**: 민감정보가 브라우저 저장소와 console에 남지 않는다.

## 5. Assumptions

- 실제 인증, 계정 상태, 승인 상태, 제재 상태는 백엔드가 최종 판단한다.
- ERD 초안은 참고 자료이며, `api-schema.md`의 enum과 응답 구조가 프론트 구현 기준이다.
- SMS/이메일 발송 성공은 실제 수신 보장이 아니라 발송 요청 접수 성공을 의미한다.
- 기업회원 재직증명서 업로드 파일은 공개 URL로 노출하지 않는다.
- 소셜 로그인 provider 연동 상세는 백엔드 OAuth 정책 확정 후 보완한다.
