## Phase 1 — 상태 관리 & 데이터 연동

### 상태 설계

- [ ] `api-schema.md`의 enum과 실제 프론트 타입이 일치하는가?
- [ ] ERD 초안과 다른 필드가 주석 또는 TODO로 남아 있지 않고 계약 기준으로 정리되었는가?
- [ ] 로그인/가입/인증/복구 API 호출이 View가 아닌 `api/` 또는 `hooks/`에 분리되어 있는가?
- [ ] `memberStatus`, `companyApprovalStatus`, `verificationStatus`의 모든 상태가 UI에서 처리되는가?
- [ ] mock state와 실제 API 응답 매핑이 분리되어 있어 API 연결 시 컴포넌트 대수정이 필요 없도록 되어 있는가?

### 데이터 연동

- [ ] 데이터 계약: `api-schema.md`에 정의된 JSON 구조와 실제 API 호출/응답 구조가 일치하는가?
- [ ] 로그인 성공 후 내 회원 상태 재조회 또는 응답 상태 기반 route guard가 동작하는가?
- [ ] 인증번호 확인 완료 상태가 프론트 boolean이 아니라 서버 발급 `verificationToken` 기준으로 처리되는가?
- [ ] 기업 승인 상태가 새로고침 후에도 서버 재조회로 복원되는가?

### 에러 핸들링

- [ ] API 호출 실패 시 `statusCode`에 따른 공통 메시지/모달/필드 오류가 정상 노출되는가?
- [ ] 네트워크 단절 상태에서 로그인/가입/인증 요청 실패 시 재시도 가능한 안내가 표시되는가?
- [ ] 429 rate limit 응답 시 재시도 제한 안내가 표시되는가?

## Phase 2 — 기능 구현 (P1: 핵심 사용자 플로우)

> P1: 로그인, 회원가입, 계정 복구의 핵심 플로우. 이 항목들이 동작하지 않으면 기능 자체가 불가.

### 로그인

- [ ] 개인/기업 탭 전환이 같은 라우트에서 정상 동작하는가?
- [ ] 로그인 요청 중 버튼이 disabled 되어 중복 요청이 방지되는가?
- [ ] 로그인 실패 문구가 계정 존재 여부를 노출하지 않는가?
- [ ] 승인 대기 기업회원 로그인 시 서비스 진입 대신 안내 화면이 표시되는가?
- [ ] 정지/잠금/블랙리스트 계정 응답이 제한 안내 UI로 매핑되는가?
- [ ] 401 토큰 만료 시 세션 정리 후 로그인 페이지로 이동하는가?

### 회원가입

- [ ] 필수 약관 동의 전 가입 버튼이 비활성화되는가?
- [ ] 아이디 중복 확인을 완료하지 않으면 가입 요청이 차단되는가?
- [ ] 이메일/휴대폰 인증 완료 상태가 서버 발급 토큰 기준으로 처리되는가?
- [ ] 인증번호 만료/실패/재전송 쿨다운/429 상태가 UI에 표시되는가?
- [ ] 비밀번호 정책과 비밀번호 확인 불일치가 제출 전 검증되는가?
- [ ] 기업회원 필수 정보와 재직증명서 PDF 없이는 제출되지 않는가?
- [ ] PDF 확장자, MIME, size 검증 실패가 사용자에게 명확히 표시되는가?
- [ ] 사업자등록번호 중복 시 기존 담당자 개인정보가 노출되지 않는가?

### 계정 찾기/비밀번호 재설정

- [ ] `/auth/find-account`에서 개인/기업 아이디/비밀번호 찾기 라우팅이 정확한가?
- [ ] 아이디 찾기 결과가 마스킹되어 표시되는가?
- [ ] 일치 계정 없음 상황에서 계정 존재 여부를 직접 노출하지 않는가?
- [ ] 비밀번호 재설정은 인증 완료 후 서버 발급 `resetToken`이 있을 때만 가능한가?
- [ ] reset token 만료 시 인증 재시작 안내가 표시되는가?
- [ ] 새 비밀번호가 기존 아이디/이메일과 과도하게 유사한 경우 정책에 따라 차단되는가?

## Phase 3 — 연동 계약 (P2: 인접 도메인 연결)

> P2: 단독 기능은 동작하지만, 관리자/구독/알림 도메인과 연결되는 항목.

### 소셜 가입/기업 승인

- [ ] 소셜 provider 정보가 없거나 충돌하는 경우 안내 UI가 있는가?
- [ ] 소셜 추가정보 입력에서 휴대폰 인증과 필수 약관 동의가 적용되는가?
- [ ] 기업 승인 대기/승인/반려/보완 필요 상태가 모두 렌더링되는가?
- [ ] 반려/보완 사유 표시 시 내부 심사 정보나 담당자 개인정보가 노출되지 않는가?

### 인접 도메인 연결

- [ ] 관리자 승인/제재 상태 변경 후 사용자 프론트에서 재조회 시 상태가 반영되는가?
- [ ] 승인 대기/제재 회원이 subscription 또는 billing route로 직접 진입할 때 제한 처리가 되는가?
- [ ] 이메일/SMS 발송 실패가 인증 UI에 일관된 방식으로 표시되는가?

## 보안

- [ ] access token, refresh token, password, verification code가 `localStorage`에 저장되지 않는가?
- [ ] 비밀번호와 인증번호가 console/debug 로그로 출력되지 않는가?
- [ ] `dangerouslySetInnerHTML`로 사용자/기업 입력값을 렌더링하지 않는가?
- [ ] 로그인 실패 횟수, 블랙리스트 기준, 제재 상세 내부 사유가 노출되지 않는가?
- [ ] rate limit 응답을 무한 재시도로 우회하는 UI가 없는가?

## 접근성 및 반응형

- [ ] 탭, 버튼, 체크박스, 모달이 키보드로 조작 가능한가?
- [ ] 오류 메시지가 관련 입력 필드와 시각적으로/접근성 속성으로 연결되어 있는가?
- [ ] 모바일 375px에서 입력 필드와 버튼 텍스트가 겹치지 않는가?
- [ ] 인증번호 타이머와 오류 메시지가 스크린리더에 전달 가능한가?
- [ ] 모달 열림/닫힘 시 포커스 이동이 적절한가?
