# Constitution: Community

**Feature Branch**: `007-community`

## 1. 도메인 원칙

> 이 도메인이 존재하는 이유와 핵심 책임을 3줄 이내로 정의한다.

* Community는 사용자가 취업 준비 과정에서 질문, 경험, 정보를 공유하는 커뮤니티 도메인이다.
* 이 도메인은 게시글 조회, 검색, 카테고리 분류, 인기글 노출, 사용자 상호작용을 제공한다.
* Community는 게시글 데이터를 제공하며, 회원 인증 및 권한 관리는 Auth/User 도메인에서 담당한다.

## 2. 상태 머신

```txt
DRAFT
  ↓ (게시글 등록)
PUBLISHED
  ↓
ARCHIVED

PUBLISHED
  ↓
DELETED
```

| 전이                   | 허용 여부 | 사유                              |
| -------------------- | ----- | ------------------------------- |
| DRAFT → PUBLISHED    | 허용    | 사용자가 게시글을 등록할 수 있다.             |
| PUBLISHED → ARCHIVED | 허용    | 오래된 게시글을 보관 처리할 수 있다.           |
| PUBLISHED → DELETED  | 허용    | 작성자 또는 관리자가 삭제할 수 있다.           |
| ARCHIVED → PUBLISHED | 허용    | 보관된 게시글을 다시 노출할 수 있다.           |
| DELETED → PUBLISHED  | 금지    | 삭제된 게시글은 복구 정책 없이 복원할 수 없다.     |
| ARCHIVED → DRAFT     | 금지    | 이미 공개된 게시글을 임시 저장 상태로 되돌리지 않는다. |

## 3. 아키텍처 결정

> 왜 이렇게 설계했는지 이유까지 적는다. 이유 없는 결정은 나중에 깨진다.

| 결정                  | 내용                                    | 근거                                 |
| ------------------- | ------------------------------------- | ---------------------------------- |
| 게시글 중심 구조           | 모든 기능은 게시글 데이터를 기준으로 동작한다.            | 커뮤니티의 핵심 자산은 게시글 데이터이기 때문이다.       |
| Entity와 DTO 분리      | Controller 응답에 Entity를 직접 노출하지 않는다.   | 데이터 구조 변경 영향을 최소화하기 위함이다.          |
| Service 중심 처리       | 게시글 생성, 수정, 삭제는 Service에서 처리한다.       | 비즈니스 규칙을 한 곳에서 관리하기 위함이다.          |
| Repository 직접 접근 제한 | Controller에서 Repository를 직접 호출하지 않는다. | 계층 구조를 유지하기 위함이다.                  |
| Mock Data 우선 허용     | 백엔드 연동 전 프론트 화면을 Mock Data로 구현할 수 있다. | UI 선개발을 가능하게 하기 위함이다.              |
| 검색 및 카테고리 지원        | 게시글은 검색과 카테고리 필터를 지원한다.               | 사용자가 원하는 정보를 빠르게 찾을 수 있어야 하기 때문이다. |
| 비로그인 사용자 접근 허용      | 게시글 조회는 누구나 가능하다.                     | 커뮤니티 접근성을 높이기 위함이다.                |
| 인증 사용자 작성 허용        | 게시글 작성은 로그인 사용자만 가능하다.                | 스팸 및 비정상 게시글 등록을 방지하기 위함이다.        |

## 4. 불변 규칙 (Invariants)

> "항상 참이어야 하는 조건"을 나열한다. 코드 어디서든 이 규칙이 깨지면 버그다.

* 게시글은 반드시 작성자 식별자(authorId)와 연결되어야 한다.
* 게시글은 반드시 제목(title)을 가져야 한다.
* 게시글은 반드시 본문(content)을 가져야 한다.
* 삭제된 게시글은 일반 목록 조회에서 노출되지 않는다.
* 인기 게시글은 좋아요, 조회수 등의 기준으로 계산된다.
* Entity를 Controller 응답으로 직접 반환하지 않는다.
* 비로그인 사용자는 게시글 작성 기능을 사용할 수 없다.
* 프론트엔드 화면은 데이터가 없거나 일부 누락되어도 깨지지 않아야 한다.

## 5. 연동 계약

> 다른 도메인 또는 외부 시스템과의 경계를 명시한다.

* Auth/User 도메인을 통해 사용자 인증 및 권한을 확인한다.
* Member 도메인으로부터 작성자 정보를 조회할 수 있다.
* Notification 도메인이 존재할 경우 댓글, 좋아요 알림을 전달할 수 있다.
* 관리자(Admin) 도메인은 신고 게시글 관리 기능을 수행할 수 있다.
* 커뮤니티는 사용자 프로필 정보를 직접 관리하지 않는다.

## 6. 금지 패턴

> 실수하기 쉬운 안티패턴을 명시한다.

* Swagger 어노테이션을 Controller에 직접 작성 금지 → `docs/CommunityDocs.java` 인터페이스로 분리.
* Controller에서 Repository 직접 호출 금지.
* Controller에서 비즈니스 로직 작성 금지.
* Entity를 API 응답으로 직접 반환 금지.
* 상태값을 문자열로 직접 비교하거나 하드코딩 금지 → Enum 사용.
* 비로그인 사용자가 게시글 작성 기능에 접근하도록 구현 금지.
* 데이터가 없을 때 빈 화면 또는 에러 화면만 노출하는 방식 금지 → 빈 상태 안내 UI 제공.
* 프론트엔드에서 관리자 페이지 또는 다른 도메인 파일을 임의 수정 금지.
* 게시글 카드 클릭 이벤트와 북마크 클릭 이벤트가 충돌하도록 구현 금지.
* 키보드 접근성을 무시한 인터랙션 구현 금지.
