# Feature Specification: 사용자 채용 공고

**Spec Branch**: `feature/jobnotice-domain-spec`
**Implementation Branch Pattern**: `feature/user-jobNotice-{세부기능명}`
**Status**: Draft

## User Scenarios & Testing

### User Story 1 - 공고 목록 탐색 (Priority: P1)

> 구직자는 채용 공고 목록에서 현재 공개된 공고를 카드 형태로 확인하고, 원하는 공고를 빠르게 찾을 수 있다.

**Acceptance Scenarios**:
1. **Given** 공개된 채용 공고가 존재할 때, **When** 사용자가 `/jobs` 목록 페이지에 진입하면, **Then** 공고 카드 목록과 전체 공고 통계가 표시된다.
2. **Given** 목록에 여러 공고가 있을 때, **When** 사용자가 공고 카드를 선택하면, **Then** 선택한 공고의 상세 드로어가 열린다.
3. **Given** 검색어 입력창이 표시되어 있을 때, **When** 사용자가 회사명, 공고명, 직무, 태그, 기술 스택, 출처 중 하나를 입력하고 검색하면, **Then** 해당 키워드와 일치하는 공고만 표시된다.

---

### User Story 2 - 조건 필터링과 정렬 (Priority: P1)

> 구직자는 직무, 경력, 채용 유형, 지역, 기업 규모, 게시 기간, 정렬 기준을 조합하여 공고 목록을 좁힐 수 있다.

**Acceptance Scenarios**:
1. **Given** 사용자가 직무 필터에서 `백엔드`를 선택했을 때, **When** 목록이 갱신되면, **Then** 백엔드 직무와 관련된 공고만 표시된다.
2. **Given** 사용자가 여러 필터를 선택했을 때, **When** 활성 필터 칩을 확인하면, **Then** `전체`가 아닌 조건만 칩으로 표시된다.
3. **Given** 활성 필터 칩이 표시되어 있을 때, **When** 사용자가 칩을 클릭하면, **Then** 해당 필터만 `전체`로 초기화되고 목록이 다시 갱신된다.
4. **Given** 사용자가 `최신순` 또는 `조회순`을 선택했을 때, **When** 정렬 메뉴가 닫히면, **Then** 선택한 기준으로 공고 카드 순서가 변경된다.

---

### User Story 3 - 공고 상세 확인 (Priority: P1)

> 구직자는 목록에서 선택한 공고의 상세 채용 조건과 기업 정보를 현재 탐색 맥락을 유지한 채 확인할 수 있다.

**Acceptance Scenarios**:
1. **Given** 사용자가 목록 카드 또는 키보드 Enter/Space로 공고를 선택했을 때, **When** 상세 드로어가 열리면, **Then** 회사명, 공고 제목, 경력, 고용 형태, 근무 지역, 마감일, 출처가 표시된다.
2. **Given** 상세 드로어가 열려 있을 때, **When** 사용자가 `공고 상세` 탭을 확인하면, **Then** 담당 업무, 자격 요건, 우대 사항, 전형 절차, 근무 조건, 마감 정보가 표시된다.
3. **Given** 상세 드로어가 열려 있을 때, **When** 사용자가 `기업 정보` 탭을 선택하면, **Then** 회사명, 업종, 기업 규모, 기업 소개가 표시된다.
4. **Given** 상세 조회 API가 응답을 반환했을 때, **When** 상세 데이터가 목록 요약 데이터보다 더 많은 필드를 포함하면, **Then** 상세 드로어는 상세 API의 최신 값을 우선 표시한다.
5. **Given** 상세 드로어가 열려 있을 때, **When** 사용자가 닫기 버튼, 오버레이, Escape 키 중 하나를 사용하면, **Then** 드로어가 닫히고 목록 탐색 상태는 유지된다.

---

### User Story 4 - 스크랩과 개인화 액션 (Priority: P2)

> 구직자는 관심 있는 공고를 목록 또는 상세에서 스크랩하거나 해제할 수 있다.

**Acceptance Scenarios**:
1. **Given** 로그인한 사용자가 스크랩되지 않은 공고를 보고 있을 때, **When** 목록 또는 상세의 북마크 버튼을 클릭하면, **Then** 해당 공고는 스크랩 상태로 표시된다.
2. **Given** 스크랩된 공고가 표시되어 있을 때, **When** 사용자가 다시 북마크 버튼을 클릭하면, **Then** 해당 공고의 스크랩이 해제된다.
3. **Given** 스크랩 상태가 목록과 상세에 동시에 표시될 때, **When** 한쪽에서 스크랩 상태를 변경하면, **Then** 같은 공고 `id`를 가진 다른 화면 상태도 동일하게 갱신된다.
4. **Given** 비로그인 사용자가 북마크 버튼을 클릭했을 때, **When** 인증 상태가 확인되면, **Then** 로그인 필요 안내 또는 로그인 페이지 이동이 제공된다.

---

### User Story 5 - 원본 공고 이동 (Priority: P2)

> 구직자는 Career Wave에서 공고를 검토한 뒤 원본 채용 사이트로 이동해 최신 조건을 확인할 수 있다.

**Acceptance Scenarios**:
1. **Given** 상세 공고에 `originalUrl`이 있을 때, **When** 사용자가 원본 공고 버튼을 클릭하면, **Then** 원본 URL이 새 탭으로 열린다.
2. **Given** `originalUrl`이 없고 공고 제목이 있을 때, **When** 사용자가 원본 공고 버튼을 클릭하면, **Then** 공고 제목 기반 검색 URL이 새 탭으로 열린다.
3. **Given** 원본 이동 URL을 구성할 수 없을 때, **When** 상세 드로어가 렌더링되면, **Then** 원본 이동 버튼은 비활성화되고 사용자 안내가 표시된다.

---

### User Story 6 - 빈 결과, 오류, 반응형 사용성 (Priority: P2)

> 구직자는 조건에 맞는 공고가 없어도 현재 상태를 이해하고 다시 탐색할 수 있으며, 모바일에서도 동일한 기능을 사용할 수 있다.

**Acceptance Scenarios**:
1. **Given** 검색과 필터 조합에 일치하는 공고가 없을 때, **When** 목록 영역이 렌더링되면, **Then** 빈 상태 메시지와 조건 완화 안내가 표시된다.
2. **Given** 목록 또는 상세 API가 실패했을 때, **When** 오류 상태가 렌더링되면, **Then** 오류 메시지와 재시도 또는 닫기 액션이 표시된다.
3. **Given** 모바일 화면에서 사용자가 목록 페이지와 상세 드로어를 사용할 때, **When** 주요 UI를 확인하면, **Then** 텍스트가 겹치지 않고 한 열 또는 드로어 레이아웃으로 사용할 수 있다.
4. **Given** 사용자가 페이지 하단으로 스크롤했을 때, **When** 상단 이동 버튼을 클릭하면, **Then** 페이지 최상단으로 부드럽게 이동한다.

## Edge Cases

- 검색어가 공백만 포함된 경우: 프론트엔드는 `trim()` 결과가 빈 문자열이면 `keyword`를 API 요청에서 제외하고 전체 검색으로 처리한다. 서버도 공백-only `keyword`를 받은 경우 필터를 적용하지 않는다.
- 기간 필터에서 기준 날짜: API 연동 후에는 서버 현재일을 기준으로 `today`, `7d`, `30d`, `all`을 계산한다. mock 데이터 단계에서는 서버 기준일을 받을 수 없으므로 데이터의 최신 `postedAt`을 기준일로 사용하고, API 전환 시 제거한다.
- 경력 조건이 `경력무관`, `신입`, `3~20년`처럼 범위가 다른 경우: `경력무관`은 `[0, 99]`, `신입`은 `[0, 0]`, `N~M년`은 `[N, M]`, `N년 이상`은 `[N, 99]`로 정규화하고 두 범위가 하나라도 겹치면 포함한다.
- API 응답은 성공했지만 `items`가 빈 배열인 경우와 API 오류 구분: `success=true`와 `items=[]`는 빈 결과 UI를 표시한다. HTTP 실패 또는 `success=false`는 오류 UI와 재시도 액션을 표시하며 빈 결과로 대체하지 않는다.
- 상세 조회가 실패한 경우: 목록 카드는 유지하고 상세 드로어 안에서 오류 상태를 표시한다. 사용자는 드로어를 닫거나 재시도할 수 있어야 한다.
- 상세 조회 중 선택 공고가 바뀐 경우: 이전 요청 결과가 늦게 도착해도 현재 선택된 공고 `id`와 다르면 화면에 반영하지 않는다.
- 스크랩 토글 요청이 실패했을 때 낙관적으로 바뀐 버튼 상태: 프론트엔드는 이전 `bookmarked` 값을 저장한 뒤 낙관적으로 갱신하고, 실패 시 이전 값으로 롤백하며 `message` 또는 기본 실패 문구를 토스트/인라인 안내로 표시한다.
- 원본 공고 URL이 없는 공고를 상세로 열었을 때 원본 이동 버튼 fallback: `originalUrl`이 없으면 공고 제목으로 구성한 검색 URL을 새 탭으로 열고, 검색 URL도 생성할 수 없는 경우 원본 이동 버튼을 비활성화하고 안내 문구를 표시한다.
- 상세 필드 일부가 비어 있는 경우: 빈 섹션을 무조건 노출하지 않고, 사용할 수 있는 정보만 표시하거나 “원본 공고에서 확인” 안내를 제공한다.

## Requirements

### Functional Requirements

- **FR-001**: 사용자는 채용 공고 목록 페이지에서 공개 채용 공고 카드를 확인할 수 있어야 한다.
- **FR-002**: 공고 카드는 회사명, 공고 제목, 직무/경력/채용 유형/지역 요약, 태그, 마감 정보, 출처, 조회수, 추천 여부, 스크랩 상태를 표시해야 한다.
- **FR-003**: 사용자는 회사명, 공고명, 직무, 태그, 기술 스택, 출처를 대상으로 키워드 검색을 수행할 수 있어야 한다.
- **FR-004**: 사용자는 직무, 경력, 채용 유형, 지역, 기업 규모 필터를 조합해서 목록을 좁힐 수 있어야 한다.
- **FR-005**: 사용자는 `오늘`, `7일`, `30일`, `기간 전체` 기준으로 게시 기간을 필터링할 수 있어야 한다.
- **FR-006**: 사용자는 `추천순`, `최신순`, `조회순` 중 하나로 목록을 정렬할 수 있어야 한다.
- **FR-007**: 활성화된 필터는 칩으로 표시되고, 사용자는 칩을 클릭해 개별 필터를 초기화할 수 있어야 한다.
- **FR-008**: 사용자는 공고 카드 또는 키보드 Enter/Space 입력으로 상세 드로어를 열 수 있어야 한다.
- **FR-009**: 상세 드로어는 선택 공고의 핵심 정보, 기술 스택, 공고 상세 탭, 기업 정보 탭을 제공해야 한다.
- **FR-010**: 상세 드로어는 목록 요약 데이터로 즉시 열 수 있고, 상세 API 응답이 도착하면 상세 필드를 보강해야 한다.
- **FR-011**: 사용자는 상세 드로어를 닫기 버튼, 오버레이 클릭, Escape 키로 닫을 수 있어야 한다.
- **FR-012**: 상세 드로어가 열려 있는 동안 배경 스크롤은 잠겨야 한다.
- **FR-013**: 사용자는 목록 카드와 상세 드로어에서 공고를 스크랩하거나 스크랩 해제할 수 있어야 한다.
- **FR-014**: 동일한 공고 `id`의 스크랩 상태는 목록, 상세, 마이페이지 스크랩 공고에서 동일해야 한다.
- **FR-015**: 사용자는 상세 드로어에서 원본 공고를 새 탭으로 열 수 있어야 한다.
- **FR-016**: 조건에 맞는 공고가 없을 때 빈 결과 메시지를 표시해야 한다.
- **FR-017**: 목록과 상세는 데스크톱, 태블릿, 모바일 화면에서 텍스트 겹침 없이 사용할 수 있어야 한다.
- **FR-018**: 검색, 필터, 정렬 변경 후 목록 개수와 화면에 보이는 카드 수는 일치해야 한다.
- **FR-019**: API 연동 시 목록 조회, 상세 조회, 스크랩 요청은 `frontend/src/user/api` 하위 API 모듈을 통해 호출해야 하며 페이지 컴포넌트에서 직접 HTTP 호출을 작성하지 않아야 한다.
- **FR-020**: API 응답은 `ApiResponse<T>`의 `success`, `statusCode`, `message`, `data` 필드 기준으로 처리해야 한다.

### Key Entities

- **JobNoticeSummary**: id, company, title, jobType, jobCategory, careerLevel, location, companySize, salary, deadline, postedAt, tags, source, recommended, recommendScore, views, bookmarked, originalUrl, stacks
- **JobNoticeDetail**: JobNoticeSummary 필드 전체, industry, responsibilities, requirements, preferredQualifications, process, workConditions, companyDescription
- **JobNoticeFilter**: keyword, jobType, jobCategory, careerLevel, location, companySize, period, sort
- **JobNoticeListStats**: totalOpenCount, todayNewCount, todayNewDelta, todayNewRate
- **BookmarkState**: id, bookmarked, scrapCount

## Success Criteria

- **SC-001**: 사용자는 페이지 진입 후 2초 이내에 첫 목록 또는 로딩 상태를 확인할 수 있다.
- **SC-002**: 검색어와 필터를 조합했을 때 화면의 공고 수와 결과 헤더의 공고 수가 항상 일치한다.
- **SC-003**: 공고 카드의 북마크 버튼 클릭은 카드 상세 열기 이벤트를 발생시키지 않는다.
- **SC-004**: 사용자는 공고 선택 후 1초 이내에 상세 드로어의 요약 정보 또는 상세 로딩 상태를 확인할 수 있다.
- **SC-005**: 상세 드로어의 닫기 버튼, 오버레이 클릭, Escape 키 닫기가 모두 동작한다.
- **SC-006**: 목록과 상세에서 같은 공고의 스크랩 상태는 항상 동일하게 보인다.
- **SC-007**: 키보드만으로 검색 입력, 필터 선택, 정렬 선택, 공고 상세 열기, 탭 전환, 원본 이동, 스크랩 토글, 상세 닫기를 수행할 수 있다.
- **SC-008**: 모바일 360px 너비에서도 주요 텍스트와 버튼이 서로 겹치지 않는다.

## Assumptions

- v1 구현은 현재 `JobNoticeListPage.tsx`와 `JobNoticeDetail.tsx`의 mock 데이터 구조를 기준으로 시작하되, API 연동 시 `api-schema.md`의 응답 구조로 전환한다.
- API 연동 전환 시 서버 상태는 TanStack Query 사용을 우선 검토하고, 검색/필터/정렬처럼 화면에 종속된 입력 상태는 React local state로 관리한다.
- 상세 페이지는 별도 라우트가 아니라 목록 페이지 안에서 `JobNoticeDetail` 드로어로 열린다.
- 상세 API 연동 전에는 목록 카드의 공고 데이터를 상세 드로어에 전달하고, 부족한 상세 섹션은 mock 또는 fallback 안내로 보강한다.
- 목록 조회와 상세 조회는 비로그인 사용자에게도 허용하지만, 스크랩 저장과 해제는 로그인 사용자만 가능하다.
- 추천순은 서버 연동 전에는 `recommendScore` 내림차순으로 처리한다.
- 최신순은 서버 연동 전에는 `postedAt` 또는 공고 ID 기준 내림차순으로 처리한다.
